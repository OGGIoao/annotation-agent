# 学习与实战路线

## 1. 学习目标

这条分支不是“先把 Agent 理论学完”，而是用一个小而完整的项目，把以下能力逐层做出来：

```text
数据契约
→ 确定性校验
→ 工作流状态机
→ 结构化模型输出
→ 多模态输入
→ 受控工具调用
→ 人工复核
→ 评测与恢复
```

每个概念都必须绑定到一个可运行实验。我们不以“看过 LangGraph 文档”作为完成标准，而以“能说明状态如何流动、能写出测试、能解释失败路径”作为完成标准。

## 2. 学习方式：四步循环

每一站固定采用以下循环：

### 第一步：先讲清一个问题

先回答：

- 这一站要解决什么真实问题？
- 不用这个设计会怎样？
- 这是模型问题、业务规则问题，还是平台问题？
- 最小输入和最小输出是什么？

### 第二步：亲手做最小实现

不直接上复杂框架。先用普通 Python 函数把机制做出来，再用 LangGraph、模型 SDK 或其他框架替换其中一部分。

这样能分清：

```text
Agent 的本质机制
≠
某个框架的 API 写法
```

### 第三步：用测试和实验观察

每站至少有：

- 正常案例；
- 边界案例；
- 失败案例；
- 一条回归测试。

实验中的数字、耗时和结论都以实际运行结果为准，不凭印象填写。

### 第四步：用自己的话复盘

每站结束后写下：

- 我现在能解释什么；
- 哪个地方仍然不懂；
- 代码中哪个边界最重要；
- 这个机制如何迁移到 `annotation-agent`；
- 哪些实验结论不能直接迁移。

## 3. 分站计划

### L0：环境和最小闭环

**目标**：在独立目录中跑通 Python、pytest、uv 和一个最小流程。

**学习**：仓库隔离、可重复环境、测试先行、输入输出边界。

**产物**：

- `experiments/l0_environment/`；
- 环境自检脚本；
- 一个能通过测试的最小 Agent 函数；
- 运行记录。

**验收**：新开终端后，按 README 命令能再次运行；测试至少有 1 个通过和 1 个预期失败案例。

### L1：数据契约和确定性校验

**目标**：让系统拒绝非法的题目框、答案框和关系。

**学习**：Pydantic、枚举、JSON Schema、领域对象、错误码、契约测试。

**产物**：

- `Question`、`AnswerBox`、`Relation`、`AnnotationResult`；
- 校验器；
- 合法/非法 fixture；
- 可读错误信息。

**验收**：不调用模型，系统能发现越界框、悬空关系、重复 ID 和绑定错误。

### L2：工作流 Agent

**目标**：把固定阶段做成有状态、可分支、可恢复的工作流。

**学习**：State、Node、Edge、条件路由、暂停、恢复、checkpoint，以及 LangGraph 与普通函数的区别。

**产物**：

```text
load_fixture
→ propose
→ validate
→ route
→ approved / needs_review / rejected
```

**验收**：至少跑出通过、需要复核、失败三条路径；流程状态可被测试读取。

### L3：结构化模型输出

**目标**：让一个模型节点提出候选，但不能绕过校验器。

**学习**：Prompt 边界、JSON Schema、结构化输出、超时、重试、截断、低置信度和模型/程序职责分离。

**产物**：可替换的 `ModelAdapter`，包括 `FakeModel` 和后续真实模型适配器。

**验收**：模型输出非法 JSON 或非法坐标时，系统进入可预期的错误或复核路径，而不是静默成功。

### L4：模拟视觉输入

**目标**：把页面图像、文字块和坐标作为证据输入。

**学习**：OCR 与视觉模型分工、原图坐标、裁剪变换、证据保留和多模态不确定性。

**产物**：简化页面 fixture、文字块、候选区域和预览图。

**验收**：结果绘制回页面后，题框和答案框位置可人工检查；坐标错误有测试覆盖。

### L5：受控工具调用

**目标**：把“应该标注什么”转换成可执行但受限制的动作。

**学习**：工具 Schema、白名单、前置条件、幂等性、动作日志、FakeExecutor 和权限边界。

**产物**：

```text
AnnotationResult
→ ActionPlan
→ FakeExecutor
→ ExecutionReceipt
```

**验收**：执行器不能接受任意动作；重复执行不会无控制地增加重复框；非法计划在执行前被拦截。

### L6：人工复核与恢复

**目标**：让无法确定的结果停下来，而不是猜测或提交。

**学习**：Human-in-the-loop、暂停/恢复、复核原因、人工决定的保留、重新校验和状态恢复。

**产物**：复核队列、复核输入、恢复测试。

**验收**：模拟“跨页不确定”或“答案候选冲突”，系统能给出最小人工问题并从决定处继续。

### L7：评测和迁移

**目标**：把玩具项目的经验映射回主项目。

**学习**：金标准、框 IoU、关系准确率、整题通过率、错误归因、成本/延迟和回归评测。

**产物**：小型评测集、评测报告、迁移清单。

**验收**：能说明哪些代码和设计可以迁移到 `annotation-agent`，哪些仅是玩具简化。

## 4. 每站的学习记录模板

每站结束时建立一个 `RETRO.md`：

```markdown
# Lx 复盘

## 我解决的问题

## 我亲手写了什么

## 运行结果

## 一个失败案例

## 失败原因

## 我现在能用自己的话解释

## 它如何对应主项目

## 不能直接迁移的地方

## 下一站前仍然不懂的问题
```

## 5. 边开发边学习的协作方式

每一站开始前，我会先给出：

1. 这一站的业务问题；
2. 最少需要理解的概念；
3. 要创建或修改的文件；
4. 预计运行的命令；
5. 验收标准；
6. 本站明确不做什么。

然后先让你理解并确认，再实施代码。完成后先给真实运行结果，再解释下一站。不跨越未验收的阶段。

你可以随时要求：

- 只讲原理；
- 先看代码再讲；
- 先做实验；
- 让我猜后再揭晓；
- 用 `roots-car` 的“章节 + 实验 + 测试 + 复盘”方式继续。

## 6. 参考 roots-car 的设计原则

从 `roots-car` 借鉴以下做法：

- **主线分站**：每站只给系统增加一种能力；
- **目标绑定**：每个概念都回答“它让小项目多了什么本事”；
- **先仿真后真实**：先 FakeModel、FakeExecutor，再接外部模型和平台；
- **三级练习**：填空式修改、只给接口、独立实现；
- **数字实测**：耗时、成功率和错误率由脚本产生；
- **测试是讲义的一部分**：练习不是靠看懂，而是由测试判断；
- **主线/选修分离**：暂时用不到的 Agent 概念单列，不阻塞主线；
- **每站都有验收标准**：不以“代码写完”作为完成。

## 7. 不照搬 roots-car 的地方

`roots-car` 的目标是从模型、强化学习到硬件的一条学习链；本项目的目标是教育题目标注工作流。因此：

- 不为了教学而自己重写所有模型；
- 不把硬件或强化学习加入当前主线；
- 不把实验仓库误当成生产标注引擎；
- 不在没有真实业务收益时引入 RAG、MCP、向量数据库或多 Agent；
- 只学习当前项目真正需要的 Agent 机制。

## 8. 第二作品的可能性

如果 L0–L7 跑通，这个实验室可以独立发展成第二个作品：

> 一个可视化、可测试、可暂停恢复的受控 Agent 工作流教学项目。

但在前期不另建远程仓库，不做对外包装。先完成可运行的本地小项目，再根据实验质量决定是否公开为 `agent-design-lab` 或类似名称。
