# 开发路线与协作约定

> 项目：annotation-agent
>
> 仓库：https://github.com/OGGIoao/annotation-agent
>
> 本文是第一版开发路线、协作方式和阶段验收标准。它不替代业务规则文档，也不替代总设计方案。

## 1. 项目目标

构建一个面向教育题目标注的多模态 Agent，将页面理解、题目拆分、答案关联、回填生成、题型属性判断和规则校验组织成可恢复、可评测的流程。

核心链路：

```text
页面输入
→ OCR/版面解析
→ 题目候选区域
→ 多模态结构理解
→ 题目树和答案关系
→ 业务规则校验
→ 局部修正或人工复核
→ 结构化结果
→ 后续平台适配
```

第一版定位为“离线标注引擎”，不是直接操作生产平台的全自动机器人。

## 2. 设计总原则

### 2.1 模型不是最终执行器

模型负责：

- 看懂页面；
- 提出题目边界候选；
- 判断题型和公共题干；
- 提出父子、跨栏、跨页关系；
- 生成答案和属性候选；
- 给出置信度和证据。

程序负责：

- 坐标归一化；
- 稳定 ID；
- 题目树；
- 关系约束；
- 规则匹配；
- 字段和格式校验；
- 最终输出契约。

人工负责：

- 低置信度样本；
- 规则冲突；
- 视觉复杂题；
- 平台结果无法自动确认的场景。

### 2.2 先建立可验证底座

不先追求“像 Agent”，而先确保：

- 输入可追踪；
- 输出结构稳定；
- 规则显式可审阅；
- 错误可以定位；
- 结果可以重复评测；
- 平台接入不会反过来污染核心领域模型。

### 2.3 每个阶段都必须有可运行产物

每个里程碑都要有：

- 可运行命令；
- 最小测试；
- 一组真实或脱敏样本；
- 明确的通过标准；
- 已知问题清单。

没有通过当前阶段验收，不进入下一阶段堆功能。

```text
annotation-agent/

│   ├── storage/             # SQLite、本地文件
│   └── observability/       # 日志、指标和追踪

├── gold-data/               # 脱敏金标准
├── sample-data/             # 本地真实样本，不提交

├── uv.lock

```

暂不拆分多个仓库。当前规则、数据契约、模型适配和平台边界都还在验证，拆分会增加接口同步成本。等平台适配或评测服务出现稳定边界后，再考虑拆仓库。

## 4. 分支和提交约定

### 4.1 分支

```text
main                    # 稳定主线
feat/contracts          # 数据契约
feat/rules-math         # 数学规则
feat/ocr-adapter        # OCR 适配
feat/graph              # 流程编排
feat/evaluation         # 评测
fix/<short-description> # 问题修复
```

小改动可以直接进入主线；涉及规则、数据契约、平台 payload 或模型接口的改动，建议使用分支和 Pull Request。

### 4.2 提交

使用单一目的、可读的提交信息：

```text
feat: add annotation contract models
feat: add math no-answer rules
fix: validate cross-page relation
chore: update rule fixtures
docs: clarify answer source policy
```

一次提交不要同时混入无关重构、格式化和业务规则变更。

### 4.3 提交前检查

```bash
cd /Users/ioao/IOAOEDU/annotation-agent

uv run python -m compileall app tests
 git diff --check
```

## 5. 阶段路线

## 阶段 0：业务和数据基线

### 目标

把业务规则从自然语言文档转成可执行、可测试的规则资产。

### 工作内容

- 固定第一版只做数学；
- 固定题型范围；
- 准备真实页面和答案页；
- 制作人工金标准；
- 记录规则冲突和最终决策；
- 定义第一版验收指标。

### 需要的输入

- 30–50 页真实题目页面；
- 对应答案页；
- 至少 20 页人工确认标注；
- 普通题、父子题、跨栏、跨页、无答案和复合题样本。

### 交付物

```text
sample-data/
gold-data/
rules/
docs/decisions/
```

### 通过标准

- 每个样本有唯一 ID；
- 金标准字段明确；
- 规则冲突有书面决策；
- 能区分题目框、答案框、关系和属性；
- 不依赖模型也能执行基础结构校验。

## 阶段 1：数据契约和确定性校验

### 目标

先搭建“不会乱”的底座。

### 工作内容

实现：

- `BoundingBox`；
- `QuestionNode`；
- `AnswerBox`；
- `AnswerLink`；
- `AnnotationResult`；
- 坐标校验；
- 父子关系校验；
- 跨页和跨栏关系校验；
- 答案框题号绑定校验；
- 虚线和答案来源枚举；
- 规则命中记录。

### 通过标准

- 非法 JSON 无法进入领域层；
- 越界框、反向坐标、悬空关系能被发现；
- 重复独立答案关联能被发现；
- 固定规则案例全部通过；
- 每个失败都有可读错误码。

## 阶段 2：单页离线解析

### 目标

完成“图片到页面中间表示”。

### 工作内容

- 接入 PaddleOCR/PP-StructureV3；
- 保存文字块和坐标；
- 统一原始页面坐标；
- 生成题号、栏位、横线和作答区候选；
- 保存 OCR 版本和图像哈希；
- 做解析缓存。

### 通过标准

- 真实页面可以重复解析；
- OCR 结果包含文字和坐标；
- 裁剪坐标可以还原到原图；
- 解析失败可说明原因；
- 不把 OCR 结果误称为最终题目框。

## 阶段 3：结果可视化

### 目标

让每次模型和规则输出都能被人看懂。

### 工作内容

把结构化结果画回页面：

- 红色题目框；
- 黄色答案框；
- 父子关系；
- 跨栏和跨页标识；
- 题型、回填答案、置信度；
- 校验错误。

### 通过标准

- 框能准确画回原图；
- 页面坐标和裁剪坐标不偏移；
- 错误可以定位到题目 ID 和字段；
- 人工无需阅读原始 JSON 就能审核结果。

## 阶段 4：多模态理解

### 目标

让模型只负责页面理解和候选生成。

### 工作内容

接入可替换的多模态模型适配器，输出：

- 题目边界；
- 公共题干；
- 子题归属；
- 父子、跨栏、跨页候选；
- 题型；
- 答案来源；
- 回填答案；
- 封闭性；
- 置信度和证据。

### 约束

- 输出严格 JSON；
- 必须通过 Pydantic；
- 首轮按页面或题组调用；
- 不为每个字段单独调用；
- 不能直接写数据库；
- 不能跳过业务校验。

### 通过标准

- 模型输出可稳定解析；
- 关键字段缺失会失败而不是静默通过；
- 低置信度能进入复核；
- 模型版本和 Prompt 版本可追踪。

## 阶段 5：规则引擎和 LangGraph 编排

### 目标

把可独立运行的解析、模型和校验节点组织成可恢复流程。

### 流程

```text
接收
→ 输入校验
→ 解析缓存/OCR
→ 候选区域
→ 多模态理解
→ Pydantic 校验
→ 题目树构建
→ 规则校验
→ 最多一次局部修正
→ 人工复核或保存
```

### LangGraph 负责

- 节点顺序；
- 中间状态；
- 条件分支；
- 超时；
- 恢复；
- 人工介入后继续；
- 局部修正次数。

### LangGraph 不负责

- 计算坐标；
- 隐式决定规则；
- 代替 Pydantic；
- 代替业务校验器；
- 无限重试模型。

### 通过标准

- 流程状态可查询；
- 失败节点可定位；
- 可从人工复核节点恢复；
- 最多一次局部修正得到程序控制；
- 超时不会阻塞任务。

## 阶段 6：多页和答案关联

### 目标

处理真实业务中最容易出错的结构关系。

### 工作内容

- 跨栏；
- 跨页；
- 跨包残题；
- 独立答案候选；
- 答案来源；
- 父子题答案绑定；
- 答案重复关联检查。

### 通过标准

- 关系方向和对象稳定；
- 只关联一次独立答案；
- 子题答案不挂错父题；
- 跨页后半题属性正确；
- 关系错误能定位到具体 ID。

## 阶段 7：人工复核

### 目标

不让 Agent 在不确定时乱提交。

### 进入复核的条件

- 题号不确定；
- 父子边界冲突；
- 答案页多个候选；
- OCR 与视觉结果冲突；
- 题型置信度低；
- 规则互斥；
- 坐标严重重叠或越界；
- 平台 payload 无法确认。

### 复核记录

- 复核原因；
- 修改字段；
- 复核结果；
- 复核人；
- 恢复节点；
- 最终是否提交。

## 阶段 8：平台适配

### 目标

把内部 `AnnotationResult` 转换成标注平台能够接受的格式。

### 结构

```text
平台任务/图片
→ Platform Adapter
→ 内部 AnnotationResult
→ Platform Payload
→ 测试任务保存
→ 人工确认
→ 才考虑生产提交
```

### 先确认

- 任务领取接口；
- 图片下载接口；
- 标注读取接口；
- 标注提交接口；
- 框和关系数据格式；
- 保存和提交状态机；
- 是否只能通过浏览器操作。

平台适配不能反向改变核心领域模型。

## 阶段 9：评测和性能

### 质量指标

- 题目框 IoU；
- 答案框 IoU；
- 子题准确率；
- 父子/跨栏/跨页关系准确率；
- 独立答案匹配准确率；
- 回填答案准确率；
- 题型准确率；
- 虚线类型准确率；
- 封闭性准确率；
- 整题一次通过率；
- 转人工率；
- 超时率。

### 性能指标

- 平均延迟；
- P95 延迟；
- OCR 耗时；
- 模型耗时；
- 校验耗时；
- 保存耗时；
- 队列等待时间。

十秒目标必须以真实样本实测，不在没有数据时承诺。

## 6. 第一版范围建议

第一版只做数学基础题型：

- 选择题；
- 填空题；
- 判断题；
- 口算题；
- 计算题；
- 解答题；
- 连线题。

第一版只支持：

- 单题框；
- 父子题框；
- 跨栏；
- 相邻页跨页；
- 独立答案；
- 有答案/无答案/二维码答案；
- 虚线类型；
- 回填答案；
- 封闭性。

暂不加入：

- 全学科；
- 听力；
- 复杂作图；
- 手写识别；
- 自动扫码；
- 生产自动提交；
- Kubernetes；
- 多仓库拆分。

## 7. 新手开发时的判断方法

遇到一个新需求，按这个顺序判断：

### 第一步：它是业务规则、模型能力还是平台能力？

- “无答案连线题仍需答案框”是业务规则；
- “识别公共题干”是模型能力；
- “把结果提交到页面”是平台能力。

不要把三类问题塞进同一个节点。

### 第二步：它能不能确定性判断？

能确定的交给程序：

- 坐标越界；
- ID 重复；
- 父框不包含子框；
- 答案框编号不匹配；
- 规则动作冲突。

不能稳定确定的交给模型或人工：

- 题目边界；
- 题型语义；
- 答案页匹配；
- 是否公共题干。

### 第三步：先加测试还是先写代码？

新增题型、关系或答案规则时，先写一个最小标准案例，再实现。

### 第四步：结果错在哪里？

按层排查：

```text
图片/裁剪
→ OCR
→ 候选区域
→ 模型理解
→ Pydantic
→ 规则
→ 关系构建
→ 平台适配
```

不要看到最终框错了，就直接修改 Prompt。

## 8. 开源和安全策略

仓库目前建议先保持私有，至少完成数据脱敏和平台边界确认后再公开。

不能提交：

- API Key；
- 登录凭据；
- 真实题目和答案图片；
- 用户数据；
- 内部任务 ID；
- 未脱敏平台接口；
- 包含敏感信息的模型响应。

公开前必须检查：

```bash
git grep -n -I -E 'sk-|token|password|secret|api[_-]?key' -- . ':!uv.lock'
git status --short
git diff --check
```
